# REQ-203 板端实施方案（自建 GATT 服务）

| 项 | 内容 |
|---|---|
| 文档编号 | DOC-12 |
| 版本 | v0.4 / S1–S5 真机通过，S6 部分完成 |
| 前置结论 | 串口透传服务的字符设备封装不可用（`rt_ble_serial_dev_register` 在 `bf0_sibles_console.c`，开启即把 console 切到 BLE，代价不可接受） |
| 采用方案 | 照 `src/ble_hid.c` 的既有模式自建 GATT 服务 |

## 1. 服务设计

| 项 | 设计 |
|---|---|
| Service UUID | 128-bit 私有：`c0de0001-5f1f-4b1e-9c3a-706f6d6f0001`（写死在 `src/ble_file.c`，注意是小端字节序） |
| Char 1 `cmd` | `c0de0002-…`，`WRITE_REQ`/`WRITE_COMMAND`，收 `V` / `L` / `G <name>`，带 RI |
| Char 2 `data` | `c0de0003-…`，`NTF`，回 `V1/F/OK/B/D/E/X`，带 CCCD |
| 权限 | `PERM(SVC_AUTH, NO_AUTH)`，与 HID 一致（免密） |
| 广播 | **不改**。仍广播 HID，主机连上后再按 UUID 找本服务（改动面最小、不影响已验证的 HID） |

## 2. 数据通路

- 收：`sibles_register_cbk(srv, get_cb, set_cb)` 的 set 回调里按字节积累，遇到 `\n` 解析；解析必须极轻（只置标志/入队），不在这里读文件。
- 发：`sibles_write_value(conn_idx, &value)`，value.idx 指向 `data` 特征。
- 传输：`G` 命令交给**独立工作线程**（`memo_ble`），从 TF 逐块读 → 转 hex → notify，带重试与退出标志。
- 忙判定：录音/回放中回 `X 9`；同一时刻只允许一个传输（`transfer_active` 标志）。

## 3. 关键风险与对策

| # | 风险 | 对策 |
|---|---|---|
| R1 | ATT 表索引/CCCD 写错，连接即崩 | 完全对照 `ble_hid.c` 的表结构（SVC/CHAR/VAL/CCCD 顺序），`HIDS_ATT_NB` 式枚举；先只跑 `V` 验证 |
| R2 | MTU 小（默认 23）导致每个 notify 只有 20 B 载荷 | 连接后打印 MTU 并主动 `sibles_exchange_mtu()`；按 `(mtu-7)/2` 动态分块（8–192 B）。实测 30 s 录音约 960 KB，若 MTU=247（原始 120 B/帧）约 8000 次 notify，估 1–3 分钟 |
| R3 | notify 拥塞（返回 0） | 每块重试 20 次、每次 10 ms，仍失败则打印进度并结束传输（主机按“文件未正常结束”丢弃） |
| R4 | 与 TF 写入/回放争用 SPI1 | 传输前检查录音/回放忙 → `X 9`；传输期间置标志，UI 侧录音入口也拒绝 |
| R5 | 主机中途断开 | 工作线程检测 `ble_file_connected()` 为假即退出，清理标志 |
| R6 | 长文件名/越界 | 只接受 `memoNNNN.wav`（长度 12、前缀后缀校验），路径拼接固定 `/` 开头 |
| R7 | **在 BLE 事件回调线程里注册服务会卡住上电**（实测：HID 不再初始化、没有广播，也没有 `svc ready` 日志） | `BLE_POWER_ON_IND` 只置 flag + 释放信号量；`sibles_register_svc_128()` 与 `sibles_exchange_mtu()` 全部搬到 `memo_ble` 工作线程执行，与 SDK `example/ble/file_transfer` 的 “Handle in own thread to avoid conflict” 一致 |

### 4.1 S1/S2 执行记录（2026-11-12）

- 128-bit UUID 在代码里按 BLE 规定**小端**存放（`01 00 6f 6d …`），与 canonical 文本相反，改动 UUID 时别直接照抄字符串。
- 编译：`F:\ascii\build_sdk.ps1 -ProjectPath F:\ascii\pomo\project` → `SCONS_EXIT=0`，`src/ble_file.o` 正常产出，无告警。
- S2：`src/main.c` 增加 `memo_tf_busy()`（录音/回放忙判定），`ble_hid_init()` 之后调用 `ble_file_init(memo_tf_busy)`；
  重新编译 `SCONS_EXIT=0`，`main.bin` 905,192 B（接入前 903,304 B，+1,888 B；再加录音红点后 905,432 B），`nm` 可见 `ble_file_init/worker/notify` 已链入。
- 主机端 `tools/ble_memo_sync/sync.py` 的 `SERVICE_HINT` 已同步为 `c0de0001`（S5 之前必须与板端一致）。
- **真机（2026-11-12，COM5，sftool verify）**：串口依次输出
  `[blefile] registering service...` → `service handle=2002d28c` → `svc ready (svc=c0de0001 cmd=c0de0002 data=c0de0003)`，
  同时 HID `service_init` / `ADV started status=0 mode=0` 正常；Windows 侧能扫到 `POMO_MEMO_HID`。
- **踩坑（已修）**：第一版在 `BLE_POWER_ON_IND` 回调里直接调用 `sibles_register_svc_128()`，导致整个 BLE 上电流程卡住
  （连 HID 的 `event BLE_POWER_ON_IND received` 都不再出现、无广播）；改为工作线程执行后恢复，见 R7。

### 4.2 上板验收清单（S3–S6，板子接上后按序做）

1. 烧录 `project/build_sf32lb52-lchspi-ulp_hcpu/main.bin`，串口（COM5 / 1000000）确认：
   `[blefile] init done, waiting BLE power on` → `[blefile] svc ready (svc=c0de0001 cmd=c0de0002 data=c0de0003)`；
   HID 仍可配对（广播名 `POMO_MEMO_HID`）。
2. 手机 nRF Connect：连接 → 找到服务 `c0de0001-…` → 订阅 `c0de0003`（notify）→ 写 `V` 到 `c0de0002` → 期望 `V1 <条数>`。
3. 写 `L` → 期望若干 `F memoNNNN.wav <size>` 后 `OK`；记录 `[blefile] mtu=… chunk=…` 一行。
4. 写 `G memo0000.wav` → 期望 `B/​D…/E`；PC 侧 `python tools\ble_memo_sync\sync.py --pull --out memos`
   （先 `pip install bleak`）比对 SHA256 与板上一致。
5. 30 s 整条：记录板上 `[blefile] sent … in … ms` 与 MTU；若 MTU < 100，先检查主机是否发起 MTU 交换。

任何一步失败：保留当前可用固件（回退 `ble_file_init` 调用即可），不带着半成品继续。

### 4.3 主机端离线端到端（2026-11-12，板子未连时的替代验证）

`sync.py --selftest-e2e` 用与板端一致的切帧规则生成 960,044 B 负载，再按 1..(mtu-3) 字节
随机分片灌进真实收包路径，比对 SHA256，同时验证 `L` 与 `X 9`：

| MTU | 原始字节/帧 | 帧数 | 结果 | 主机处理 |
|---|---|---|---|---|
| 247 | 120 | 8,003 | SHA256 一致 | 3.3 s |
| 517 | 192 | 5,003 | SHA256 一致 | 1.9 s |
| 23 | 8 | 12,002（96 KB 样本） | SHA256 一致 | 0.1 s |

结论：分帧/重组/尺寸校验在 30 s 录音量级成立；MTU=23 时 960 KB 约需 12 万帧，空口时间不可接受，
实际必须让 MTU 协商到 247 以上（离线证据见 `evidence/2026-11-12-req203/`）。

真机对照（2026-11-12，Windows bleak 3.1.0，MTU 527 → chunk 192）：`L` 返回 13 条共 1.9 MB；
12 条短录音全量拉取成功；30 s 整条 `memo0012.wav`（960,044 B）板端日志 `sent … in 14009 ms`
（≈68.5 KB/s，5,000 帧），主机端到端 17.3 s / 26.0 s 两次；文件字节数与列表一致、WAV 头合法。
日志见 `evidence/2026-11-12-req203/pull.log`、`pull30.log`、`serial-30s.txt`。
